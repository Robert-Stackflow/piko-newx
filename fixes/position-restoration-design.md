# 时间线位置恢复：撤回结论与重设计

状态：身份恢复已实现；`listfix.6` 绑定未生效，`listfix.6.1` 切换列表出现 ANR，均拒绝交付。`listfix.6.2` 已安装，静态检查与启动通过；完整受控测试因 ADB 断开尚未完成。保留 `listfix.5` 作为回退包。

## 第一版实现范围

- 账号身份来自原生组件 owner，列表身份来自 TimelineIdentifier。通过组件委托的状态流绑定 UI 生命周期；绑定前强制经过未内联的位置 getter 注册范围，兼容 List 委托直接读取状态字段。暂停后停止观察。
- 从最终 LazyList interval provider 读取全部界面 key，不重算模块索引。第一版只接受 `RegularItem(entryId, sortIndex)`，其字段由语义字符串和构造器验证；未知 key、横向模块、标题、加载提示均跳过。纵向模块的普通帖子行可定位。
- 新存储 `piko_newx_list_anchors_v2` 不迁移旧序号。关闭原生列表 ordinal 存取路径，其他时间线沿用上游实现。
- 新项目序列发布后，等待有效的新测量结果与原生滚动结束，再发出一次非挂起 UI 位置请求。没有匹配项目或 key 重复时不使用旧序号。恢复请求完成前不重新保存中间画面。
- 80ms 的观察仅在绑定的列表生命周期中运行；没有活动列表时不再排队。持久化写入节流到 700ms，退出时补存。原始帖子内容不写日志；只记录脱敏范围标识、动作与代次。
- 绑定的 LazyList 拖动事件源和显式回顶回调取消待恢复任务。共享交互发射器保留原始行为；非绑定源只做空查找即返回。
- 第一版没有历史分页、横向模块身份恢复或跨布局像素位置保证。排序/过滤变化后只能恢复当前最终序列里仍存在且唯一的完整 key。

### ANR 后的边界修正

`listfix.6.1` 的位置恢复、拖动取消、相同帖子/边界恢复都曾被观察到，但多个列表切换触发系统 ANR，因此上述观察不能视为版本验收。系统记录为输入事件等待主线程超过 5 秒。

已找到实现里的危险依赖：最终项目 provider 的构建回调直接读取 LazyList 的 snapshot 状态（位置、layoutInfo）；provider 的计算可能因此依赖它自己参与生成的布局，造成反复计算。修正后 render 回调只登记 provider 的弱引用并排队，所有快照读取、key 遍历和恢复决策统一在独立 Handler 回调执行。该原因与现象一致，但未取得 ANR Java 主线程栈，不能单凭推断宣称所有卡死原因都已排除。

模拟测试增加了“构建期间读 snapshot 或遍历 provider 就直接失败”的回归断言，并覆盖只含未知/加载 key 的中间状态不消耗保存的身份。最终 APK 额外验证 render 不调用 native accessor、observe 或 publish；真实多列表切换仍是必要验收。

以下是原始设计及其后续验收要求。实测结果以 fixes/README.md 为准。

## 当前“恢复时间线位置”实际做什么

分析基线：Piko `bc03fce4352bcb7ee89299722d0e900af3fb8a82`，X `12.22.0-prod.01`，原始 APK SHA-256 `51d43aec02604d097677d0cfc68c7639046ceed6b007610aee143c007979b48f`。

相关源文件：

- `extensions/newx/src/main/java/app/morphe/extension/newx/timeline/TimelineScrollPositionStore.java`
- `patches/src/main/kotlin/app/crimera/patches/newx/timeline/RestoreTimelinePositionPatch.kt`

1. 开关 `newx.timeline.restore_position` 默认开启，改变后要求重启。
2. 保存内容只有首个可见项目的序号、像素偏移。先解析原生 holder 的字符串；失败时反射读取两个非静态 int 字段。不保存帖子内容或帖子 ID。
3. SharedPreferences 文件是 `piko_newx_timeline_positions`；键是时间线枚举名加 `.index` / `.offset`。没有账号或列表 ID，因此它本身不能区分多个 LIST_POSTS。
4. 原生组件写入内存位置表之前，补丁同步保存上述两个整数。读取时，如果内存表已有值就继续使用；没有值才从持久化存储补入原生 holder。
5. 上游补丁没有绕过原生保存/恢复策略门禁。界面加载完成后，由原生 Compose 逻辑消费 holder 并滚动；位置保存事件来自离开/暂停界面及满足条件的停止滚动事件。
6. 它解决的是进程重启后恢复“第几项”，不是刷新后找回“同一条帖子”。前面新增、删除或过滤项目后，旧序号会指向不同内容。

当前自定义层把键改为原生列表标识，并让列表保存/恢复进入单独存储，但仍只有序号/偏移，也没有账号隔离。它不能解决内容变化后的身份定位。

## 为什么撤回 listfix.4

该实验不只是恢复 UI：它让列表填充原本只供 For You 使用的可见项缓存，并把刷新交给 viewport-aware 数据合并路径，同时拦截下拉完成后的回顶。

原生合并路径能重新写入缓存的可见项目。因此它有把旧内容保留并混入刷新结果的风险，与用户报告相符；没有捕获到那一条具体旧帖的完整来源链，不能声称已单独证明其来源。

listfix.5 删除这三项干预，保留汉化、分时间线转推开关、列表标签纯文字，以及已知局限的按列表序号保存。既有缓存和登录数据不清除；撤回代码不会追溯清理先前已经写入的缓存内容。

## 新设计：记录身份，只改变视口

### 必须守住的边界

- 不新增、删除、重排或替换任何时间线数据；不切换请求模式、不写数据库、不重新插入旧帖子。
- 存储范围：账号 ID + 时间线类型 + 列表 ID + 排序方式；记录过滤配置版本，变化时重新验证目标。
- 记录最终渲染项目的稳定 key（包含模块/转推实例等上下文）、必要时的帖子 ID、像素偏移和存储结构版本。序号仅作诊断提示。
- 原始数据索引不能当作界面索引：模块、标题、广告、过滤和转推都会改变最终 Compose 项目排列。
- 不能直接把 key 的 toString 当作跨进程稳定格式；先验证 key 子类型及其可序列化身份字段。帖子 ID 回退只允许唯一匹配，不能误选同帖的另一转推实例。

### 时序与竞争处理

`等待列表绑定 → 等待有效数据 → 按最终项目 key 查找 → 校验仍是同一账号/列表/加载批次 → 恢复一次 → 交回用户控制`

- 在用户停止滚动或离开页面时保存；加载中的空列表不能以 0 覆盖待恢复锚点。
- 自动刷新前在 UI 层捕获当前 key；原生数据正常更新后，只在目标仍存在时调整视口到其新索引。
- 手动刷新：保留当前阅读项的意图与“回到顶部”分开处理；目标仍在结果中时可维持阅读项，显式回顶一定取消恢复。不会为了留住目标而改写响应。
- 用户开始拖动、切换账号/列表、显式回顶时取消待执行恢复。每次任务绑定页面实例和加载代次，迟到响应不能操作新页面。
- 恢复后的程序滚动不能当成用户输入，不能重复写入并触发循环。
- 布局、字体或屏幕变化后夹取合法偏移；偏移目标是同一个最终渲染项，不保证跨布局像素完全一致。

### 找不到原帖时

目标被删除、过滤、未加载或本轮数据替换移除时：保留原生当前视口，不套用旧序号、不补回旧帖子、不自动无限翻页。必要时给轻量提示“原位置暂不可用”。跨进程的新数据里没有原帖，就不能承诺原地恢复；如果以后需要主动加载历史内容，应作为独立选项设计。

旧序号记录不能转换成可信帖子身份，不迁移为新锚点。新存储使用独立版本，只在实际看见有效项目后建立记录。身份信息仅留设备私有存储；诊断不输出账号、帖子正文或原始列表标识。

## 实施前还需证明的字节码契约

已定位原生 holder、保存事件、位置 getter 和 Compose 的加载后滚动消费者。下一步需要解析最终项目 key 的具体变体、key 到索引的解析入口、加载代次和用户交互取消条件。上述契约未全部验证前，不注入新恢复逻辑。

生产补丁从语义字符串、类型关系、公开框架调用与唯一指令形态定位；混淆类名只作本次分析记录，不写成运行时绑定。零匹配、多匹配或分支未证明时构建失败。

## 验收矩阵

- 新项目插入前端、无新增、目标删除、目标未加载、刷新失败、空首屏。
- 同一帖子多个转推实例、线程模块、隐藏转推前后、排序改变。
- 两个列表不同位置、相同列表不同账号、切换标签、前后台、进程重启。
- 延迟响应、恢复前用户拖动、显式回顶、连续刷新、旋转及字体变化。
- 数据层不变性：位置层开/关时，最终数据 ID 顺序和数量应一致；只允许视口索引/偏移不同。
- APK 签名/对齐、最终 DEX 检查、ART 强制验证、启动无崩溃，以及隔离用户同步操作后的真实设备验证。

只有身份定位和取消条件完成上述验证，才能宣布新位置恢复已实现；启动成功不是功能验收。
